# ZIP13 security boundaries / limitations

- **PRODUCTION** enforces TLS enabled for Tracker and P2P and requires P2P hostname verification; Peer certificates need SANs matching the IP/DNS used in connections. `P2P_PROFILE=production` on Tracker and each Peer.
- `P2P_PROFILE=lan` forbids demo bypass, but can use plain TCP only on trusted LAN for compatibility testing. **LAN plain TCP is not encrypted**.
- `P2P_TLS_VERIFY_HOSTNAME` now defaults TRUE when P2P TLS is enabled. An explicitly disabled check is a **development/LAN exception only** and is not suitable for public Internet.
- P2P bitfield and piece requests require a Tracker-signed ticket plus an Ed25519 proof-of-possession signed by the requester's registered private key; the proof binds request type, uploader, file, piece, ticket hash, timestamp, and nonce. The timestamp window is 60 seconds. Uploaders keep a bounded in-memory replay guard; it is cleared on uploader restart, while the timestamp window limits the replay exposure. Metadata-page requests remain ticket-authorized because they return metadata only, not piece bytes.
- A stolen ticket alone cannot retrieve piece data; a stolen ticket together with the requester's private key remains usable only until expiry. Tracker ticket TTL defaults to 900 seconds (15 minutes), configurable with `P2P_TICKET_TTL_SECONDS` in the range 60–3600; invalid values fall back to 900 seconds with a warning.
- R77 PR 1 distributes in-memory ticket revocations for requester logout/session expiry and uploader unshare through heartbeat. Revocation is near-immediate, not absolute: maximum propagation delay is the configured heartbeat interval (10 seconds by default) plus network delay. The Tracker retains at most 10,000 entries for at least 3,900 seconds; a Tracker restart loses this in-memory list, so old tickets then remain governed by their expiry. An uploader applies its own unshare locally without waiting for heartbeat.
- Before each P2P bitfield, metadata-page, or piece request, the downloader reads the ticket expiry only to decide whether to refresh. At 60 seconds or less remaining (or if the claims cannot be parsed), it asks Tracker for fresh file sources/tickets using the current session and continues the same transfer. The uploader still verifies the ticket signature, audience, and expiry; client-side expiry parsing never grants authorization. A rejected/failed refresh ends the transfer as incomplete instead of reusing the stale ticket.
- Ticket claims include a signed `keyId`. `P2P_TICKET_KEY_ID` selects the Tracker's active ID and defaults to `default`; older single-public-key Peer configuration is associated with that ID. Peers may trust several keys with `P2P_TICKET_PUBLIC_KEY_FILES`, a semicolon-separated list of `keyId=path` entries. Rotation: (1) distribute the new public key to every Peer alongside the old key, (2) change Tracker to the matching active private key and ID, (3) after the maximum ticket TTL (3600 seconds) has elapsed, remove the old public key from Peers. Tracker holds only one active private key; rotation is operator-managed.
- On Tracker restart, a new random `trackerInstanceId` is returned by heartbeat. A Peer receiving a different ID clears its local revocation list and resets the cursor before applying the new snapshot. If the restart occurs, the in-memory revocation list is lost; outstanding tickets are still bounded by the short TTL.
- R77 policy is implemented: logout/unshare/session expiry revocation, short-lived tickets, in-transfer refresh, and key-ID-based rotation support. Revocation remains near-immediate rather than instantaneous; refresh requires a live Tracker session and a source that is still sharing.
- SHA-256 ensures integrity but not confidentiality. TLS protects transport when configured correctly. Certificate trust material and private keys must never be shipped in public builds.
- Run negative test cases: wrong Tracker key, missing Peer public key, invalid certificate SAN, wrong peer, expired ticket, restart and transfer over LAN/Relay; review logs for leaks.
