# Local demo and EC2 release (protocol v4)

## Local demonstration (developer Windows CMD)

Apply patch 12 on top of 07–11; run `gradlew.bat clean test` first. Start the existing local PostgreSQL service with its existing database/schema v9 and project-root `.env` DB credentials. The launcher reads only DB connection fields from this file (or OS variables), refuses remote hosts, and does not run migrations or alter database configuration. Do not set up a new database if one is already available. Both launchers need JDK 21, Python 3.10+ and Gradle dependencies. No Peer truststore or keys to configure.

CMD 1 (keep open): `scripts\run_local_server.cmd`

CMD 2: `scripts\run_local_client.cmd`

Optional CMD 3 for a second simultaneous Peer on the same computer: `scripts\run_local_client.cmd 2`. Use different accounts for demonstration. Slot 1 uses upload port 7001, slot 2 uses 7002; slots 1–9 are supported. Separate persisted homes, identities and download defaults live under `work/local-demo/peer-home-N` (the file chooser can still select your usual files). Do not launch the same slot twice. First startup generates a loopback-only certificate SAN, private CA and ticket signing keys into ignored `work/local-demo/profile`, and subsequent runs reuse that profile. This is separate from the installed EC2 profile; do not delete it or publish it. The underlying tracker socket may listen on other interfaces; keep Windows firewall configured for local-only testing. All Tracker and Peer data channels retain production TLS and protocol v4. If a port is occupied, stop the previous process; do not automatically fall back to another server. A fresh local PostgreSQL setup still requires an administrator to provision the DB/credentials once.

The scripts build `installDist` and start the Java mains with isolated explicit configuration. Raw `gradlew.bat :peer-client:run` and `:tracker-server:run` are unchanged; use the dedicated scripts to avoid stale production config. No EC2 is contacted by these launchers. Stop with Ctrl+C / close windows. If a provisioning operation is interrupted, inspect the ignored `provision.lock` and profile before retrying; never rotate production keys.

## EC2 administrator and distribution (later)

1. Start EC2 and confirm the actual public IP or stable hostname, DNS and certificate SAN. Existing IP 52.64.196.242 is historical only. Upgrade tracker to v4 following existing AWS handoff. Preserve PostgreSQL schema v9, CA and signing keys unless a planned rotation is necessary. Do not use the local demo CA or ticket keys on AWS.
2. Obtain only the existing EC2 CA public PEM and Tracker Ed25519 public key over the trusted administration channel, verify fingerprints out of band. Use `java scripts\CreatePublicClientBootstrap.java work\EC2_PUBLIC_BOOTSTRAP TRACKER_HOST work\ec2-ca-public.pem work\ec2-tracker-public.key.b64` (replace TRACKER_HOST with actual matching hostname/IP). If the server SAN no longer matches, reissue the server certificate under the existing CA as appropriate. Never download and automatically trust arbitrary CA or public keys from a peer or unverified endpoint.
3. `scripts\build_ec2_client.cmd work\EC2_PUBLIC_BOOTSTRAP work\FileShare-P2P-EC2` builds distribution and executable launcher JAR. Output directory and ZIP must be new. It copies only public trust material and runtime JARs; rejects unexpected config keys, private entries in truststore, invalid CA/key and loopback endpoint. The JAR launches the JavaFX application with explicit bundled config, ignoring legacy environment overrides. It does not change the existing per-user production profile or Peer identity. The EC2 and local demo identity stores are separate.
4. Distribute the entire output ZIP from a trusted channel, never send CA private key, Tracker signing private key, server keystore, database credentials or work/local-demo. User extracts whole folder and double-clicks RUN_CLIENT.cmd or runs `java -jar FileShare-P2P.jar` (Java 21 installed). No manual CA/truststore/key/env setup. This is a launcher JAR with adjacent `lib` and `CLIENT_PUBLIC_BOOTSTRAP`, NOT a standalone fat JAR or runtime installer. If Java is not installed, a separate jpackage runtime distribution is still required.
5. Verify a clean Windows user can register/login; test two distinct machines LAN and Internet, Direct/Relay, change Wi-Fi/4G, SHA-256, wrong certificate/key rejection. Demo local and EC2 are independent; no silent fallback. If AWS is offline, production connection fails rather than redirecting to a different database.
